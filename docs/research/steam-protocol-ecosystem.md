# Экосистема Steam-протокола и альтернативных клиентов

Дополнение: выбранное направление изменено на собственный host движка Valve по примеру OpenSteamClient. Он заменяет официальный desktop-процесс; ниже описанная первоначальная интеграция с запущенным Steam больше не является обязательной архитектурой. См. [исследование самостоятельного runtime](standalone-rust-runtime.md) и [актуальный план](../standalone-client-plan.ru.md).

Проверено 9 октября 2026 года. Исследование первичных репозиториев, исходников и документации; авторизация в Steam, сборка клиентов и проверка игр на реальном аккаунте не проводились. Перечень возможностей ниже означает документированную авторами поддержку, а не наш результат совместимости.

## Вывод для архитектуры

Rust подходит для ядра нового клиента, однако нет проверенной готовой Rust-библиотеки, которую можно подключить и получить все функции Steam. Полезно разделить три разные задачи: общение с серверами Steam, загрузка контента и предоставление игрового Steamworks runtime. Успешный вход через CM или загрузка depot не доказывают, что произвольная игра заработает без официального клиента.

Для первого продукта предлагается собственный интерфейс и Rust-ядро с заменяемыми адаптерами: CM для аккаунтов, библиотеки и общения; официальный Steam как первоначальный исполнитель запуска и обновления игр; официальные веб-страницы для магазина и оформления покупок. Полностью независимое исполнение Steamworks считать отдельной исследовательской программой с проверкой по играм. Это архитектурный вывод исследования, а не обещание Valve или авторов библиотек.

## Библиотеки и инструменты

### SteamKit2

SteamKit2 — .NET-библиотека SteamRE для связи со Steam Network, LGPL-2.1. Это зрелый источник протокольных реализаций и примеров; оценка зрелости основана на длительной истории и использовании в DepotDownloader, а не на тесте всех её функций. Текущая ветка master требует .NET 10, тогда как README DepotDownloader указывает .NET 8: зависимости следует фиксировать по выбранному релизу, не смешивая инструкции разных веток. [SteamKit](https://github.com/SteamRE/SteamKit), [DepotDownloader](https://github.com/SteamRE/DepotDownloader)

Для Rust возможен отдельный процесс-мост с небольшим версионированным IPC, но это дополнительный runtime, упаковка и сопровождение. Альтернатива — использовать SteamKit как эталон протокольного поведения при собственной реализации. Условия LGPL и итоговую схему распространения необходимо проверить до включения в поставку; выбор sidecar сам по себе не является универсальным освобождением от лицензионных требований.

### node-steam-user и node-steam-session

Оба проекта DoctorMcKay распространяются под MIT. `steam-user` реализует клиентский Steam-протокол, вход, сведения о лицензиях, wallet balance, presence и множество операций; современный чат вынесен в `SteamChatRoomClient`, старые chat API помечены deprecated. Это практичный референс или временный Node-sidecar, но не готовый desktop runtime для запуска любых Steamworks-игр. [steam-user](https://github.com/DoctorMcKay/node-steam-user), [современный чат](https://github.com/DoctorMcKay/node-steam-user/wiki/SteamChatRoomClient)

`steam-session` занимается аутентификацией и токенами. Нужно различать аудитории `SteamClient`, `WebBrowser` и `MobileApp`. Документация отдельно отмечает изменения от 30 апреля 2025: получение веб-cookie для SteamClient refresh token требует аутентифицированной CM-сессии; обычный вызов может вернуть AccessDenied. Успешное обновление refresh token аннулирует предыдущий. Нельзя проектировать вход как разовую выдачу вечного cookie. [steam-session](https://github.com/DoctorMcKay/node-steam-session)

### DepotDownloader

Консольный .NET-инструмент SteamRE на SteamKit2, GPL-2.0. Поддерживает загрузку app/depot/manifest, Workshop, выбор ОС, архитектуры, языка, ветки, целевого каталога и проверку checksum; есть macOS Homebrew. Имеет QR и уникальный `-loginid` для параллельных экземпляров. [Документация](https://github.com/SteamRE/DepotDownloader)

Полезен как эталон для загрузчика или экспериментальный внешний инструмент. Он не даёт готового планировщика desktop-клиента, управления Steam Cloud, игрового оверлея, магазина или общего транзакционного протокола совместного изменения библиотек с Steam. Копирование его кода в ядро требует соблюдения GPL; решение о зависимости нельзя принимать только по удобству CLI.

### steamworks-rs

`Noxime/steamworks-rs` — Rust bindings к **Steamworks SDK**, а не реализация Steam Network. Обёртка имеет MIT/Apache-2.0 с исключениями для поставляемых файлов SDK. Она динамически использует библиотеку Steam API. [Репозиторий](https://github.com/Noxime/steamworks-rs)

Valve прямо указывает: SteamAPI_Init требует работающего Steam-клиента, правильного AppID, того же OS user context и лицензии активного аккаунта. SDK полезен для интеграции собственной игры и тестового приложения, но не делает новый launcher заменой Steam. [Valve: API initialization](https://partner.steamgames.com/doc/sdk/api#initialization_and_shutdown)

## Несколько аккаунтов: четыре отдельных уровня

1. **Каталог аккаунтов.** Объединённая библиотека и выбор владельца игры реализуемы как продуктовая модель. Хранить ownership, доступные DLC, SteamID, регион/валюту и время последней проверки отдельно для каждого аккаунта. Понятие «эта игра видна в библиотеке» не заменяет актуальную проверку права запуска.
2. **Сетевые сессии.** Несколько CM-подключений возможны, но имеют ограничения. Исходник SteamKit документирует уникальный LoginID для одновременных сессий одного аккаунта с одного публичного IP. Без этого одна сессия вытесняет другую. [SteamUser.cs](https://github.com/SteamRE/SteamKit/blob/master/SteamKit2/SteamKit2/Steam/Handlers/SteamUser/SteamUser.cs)
3. **Веб-сессии.** Cookie jars, refresh tokens и UI-контекст магазина должны принадлежать конкретному SteamID. Смена выбранной карточки аккаунта не должна сохранять старую корзину, wallet или cookie нового окна. Изоляция и атомарная запись при ротации токенов — предлагаемое требование архитектуры, опирающееся на семантику токенов `steam-session`.
4. **Игровая идентичность.** Она связана с аккаунтом, который обслуживает локальный Steamworks runtime. Собственная CM-сессия аккаунта B не переключает уже работающий официальный Steam с A на B. Надёжный старт через B требует проверенного переключения runtime и проверки его фактической идентичности перед запуском. Основание: условия SteamAPI_Init выше; конкретный механизм автоматизации переключения на Mac ещё нужно исследовать.

Кроме login-сессии существует ограничение активного игрового сеанса. `steam-user` сообщает `playingState.blocked`, когда аккаунт играет через другое подключение. `gamesPlayed` лишь сообщает presence; это не запуск процесса. Параметр force может вытеснить другой сеанс, поэтому автоматическое применение недопустимо как обычное поведение launcher. [Документация playing state и gamesPlayed](https://github.com/DoctorMcKay/node-steam-user#gamesplayedapps-force)

Предлагаемая первая версия: много сохранённых аккаунтов и доступных chat/library-сессий, но один явно выбранный аккаунт игрового runtime на Mac. При переключении: убедиться, что игра завершена; дождаться синхронизации сохранений; переключить Steam; проверить SteamID и лицензию; затем запустить. Если подтверждение любого шага отсутствует, показывать понятное состояние и действие пользователю. Параллельный запуск игр под разными runtime-аккаунтами на одном macOS-пользователе не обещать без отдельного PoC.

## Загрузки и общая библиотека

Ни одна из исследованных библиотек не предоставляет доказанного протокола координации записи с официальным Steam. Поэтому ниже проектные требования, а не обнаруженная гарантия внешних инструментов:

- Для каждой установки назначить одного владельца операций: официальный Steam либо собственный загрузчик. Нельзя считать внутренний lock нашего приложения защитой от записи стороннего Steam.
- Первая версия читает существующие manifests и передаёт update/install официальному клиенту. Собственный downloader сначала работает в отдельном каталоге, который Steam не обслуживает.
- Независимый загрузчик требует staging, журнала операций, crash recovery, проверки hash, свободного места, atomic commit и возобновления загрузки. Отмена не должна оставлять установленную версию наполовину обновлённой.
- Установка и лицензия — разные сущности: общий контент не означает общие DLC, branch entitlements, сохранения или одинаковые файлы для всех аккаунтов.
- Не переключать аккаунт в середине операции, требующей его depot key или token; изменение целевого аккаунта создаёт новое задание с повторной проверкой прав.
- Сохранения и Cloud разделять по аккаунту и игре; менять только после резервного копирования и проверки конфликтов. Реальное расположение save files задаётся игрой, не универсальным SteamID-каталогом.

## Проверки до фиксации зависимостей

Короткий обязательный PoC должен сравнить выбранный Rust-кандидат с SteamKit или node-steam-user на одинаковых сценариях. Предлагаемые критерии:

1. QR и password/Guard, отмена/истечение QR, повторный вход после restart, отзыв refresh token, сетевое отключение и macOS sleep/wake.
2. Два собственных аккаунта с пересечением библиотек: корректные владельцы, DLC, wallet currency, события без смешивания данных.
3. Параллельная CM-сессия и официальный Steam: нет бесконечной борьбы reconnect и непреднамеренного отключения игры.
4. Прямые сообщения и история; отдельно group chat, голос, game invite и join. Наличие text chat не засчитывать как поддержку всех социальных функций.
5. Запуск тестовой Steamworks-игры под A и B с подтверждением SteamID самой игрой, проверка achievements/Cloud после выхода.
6. Загрузка/обновление небольшого тестового depot в отдельный каталог: обрыв сети, нехватка диска, отмена и аварийное завершение. Работа в общей библиотеке — следующий отдельный этап.
7. Проверка ARM64/x86_64 упаковки и подписания sidecar, реального потребления памяти/CPU и всех лицензий выбранного набора.

До этих проверок нельзя обещать «все функции Steam», универсальное переключение аккаунта запуска, полноценный offline mode или полный отказ от официального клиента.
