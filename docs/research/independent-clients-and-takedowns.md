# Независимые клиенты Steam: запуск игр, архитектура и заявления об удалениях

Проверено 9 октября 2026 года. Исследование первичных источников: README, исходники и сообщения авторов. Код сторонних проектов не запускался; вход в Steam, чтение локальных токенов и испытания игр не выполнялись. «Реализовано в исходниках» и «подтверждено испытанием на нашем Mac» — разные статусы.

## Исправление исходного предположения

Утверждение, что альтернативному клиенту обязательно нужно запущенное **официальное приложение Steam**, было слишком широким. Есть реализованная третья архитектура между оболочкой над работающим Steam и переписыванием Steam целиком: собственное приложение загружает закрытый движок Valve и само становится локальным сервером Steam для игр. OpenSteamworks прямо описывает режим `Global instance`: игры подключаются к процессу нового клиента, а исходное приложение не требуется. Отдельный `ExistingClient` подключается к уже запущенному Steam. Эти режимы нельзя смешивать. [OpenSteamworks: connection modes](https://github.com/OpenSteamClient/OpenSteamworks/blob/master/OpenSteamworks/README.md).

Следовательно, требование SkinOS «без Steam.app и его интерфейса» имеет технический прецедент. Требование «без любых бинарных компонентов Valve» существенно шире. Его не надо незаметно приписывать пользователю. Перенос первого подхода на современный macOS нужно проверять отдельно.

## Карта проверенных проектов

| Проект | Что заменяет | Что остаётся | Значение для SkinOS |
|---|---|---|---|
| OpenSteamClient / OpenSteamworks | Приложение и интерфейс Steam; процесс сам обслуживает локальный Steam API | `clientdll` Valve и необходимые вспомогательные компоненты | Наиболее прямой архитектурный образец для полной замены приложения при сохранении игрового backend |
| Mist — `98przem/mist` | Загрузку и запуск Windows-игр Steam на macOS без Steam client | Wine, SteamKit2/DepotDownloader, сторонняя реализация игровых Steam API | Рабочий по структуре кода пример независимого macOS launcher, но не эквивалент всех online-функций Steam |
| Argon / argonx | Саму библиотеку `steamclient.dll/.so` | Собственный протокол и ABI-совместимость | Исследовательские заготовки для независимого runtime, не готовая замена |
| SteamRE/open-steamworks | Ничего самостоятельно: набор восстановленных интерфейсов | Steam runtime, к которому обращается вызывающий код | Исторический справочник; не путать с текущим проектом OpenSteamClient/OpenSteamworks |
| dajoh/OpenSteamClient | Сетевое подключение к Steam | Клиентскую реализацию игр нужно строить отдельно | Одноимённая C++ protocol library, не полный игровой desktop client |

Источники строк: [OpenSteamworks](https://github.com/OpenSteamClient/OpenSteamworks/blob/master/OpenSteamworks/README.md), [Mist](https://github.com/98przem/mist), [Argon](https://github.com/emily33901/Argon), [argonx](https://github.com/emily33901/argonx), [SteamRE headers](https://github.com/SteamRE/open-steamworks), [dajoh library](https://github.com/dajoh/OpenSteamClient).

## 1. OpenSteamClient: важнейший прецедент

Старый адрес `Rosentti/opensteamclient` перенаправляет на живой публичный `OpenSteamClient/OpenSteamClient`. Основная ветка помечена deprecated и направляет в `c#-remake`. Это не свидетельство удаления по требованию Valve. [Основной репозиторий](https://github.com/OpenSteamClient/OpenSteamClient).

Ветка переписывания использует C#/Avalonia и закрытый `clientdll`. Автор перечисляет Windows/Linux x86-64 как целевые системы. В коде и плане есть запуск, загрузки, авторизация с 2FA, друзья и присоединение к игре. Чаты, overlay и ряд экранов ещё недоделаны; README отдельно исключает VAC-игры и игры, которым нужен ISteamHTMLSurface. Наличие пункта в roadmap не означает готовую функцию. [README c#-remake](https://github.com/OpenSteamClient/OpenSteamClient/blob/c%23-remake/README.md).

Старый Qt-форк прямо говорит, что GUI работает с `steamclient.so` и `steamservice.so`; ему не нужен `steamwebhelper`. Инсталлятор перестраивал Steam-каталоги и symlink, что объясняет несовместимость одновременного запуска двух клиентов. Для SkinOS эту схему перемещения пользовательских папок копировать не следует: отдельный runtime root и явная блокировка владельца состояния позволяют исследовать интеграцию значительно аккуратнее. Последнее предложение — наш инженерный вывод. [Qt5 fork](https://github.com/FWGS/opensteamclient-qt5).

OpenSteamworks требует точного соответствия runtime и восстановленных интерфейсов; несоответствие может дать неверный вызов функции или crash. В `Global instance` приложение получает полный внутренний ClientAPI, но обязано создать правильное окружение, обеспечить discovery процесса и вспомогательные файлы. Это означает необходимость версии ABI, startup diagnostics и отдельного helper-процесса, а не простого подключения обычного Steamworks crate. [Требования OSW](https://github.com/OpenSteamClient/OpenSteamworks/blob/master/OpenSteamworks/README.md).

Реализация `NativeSteamClient` действительно инициализирует ClientDLL, получает `IClientEngine`, обслуживает callbacks и ищет PID глобального клиента. Это подтверждает описанную архитектуру на уровне кода, а не только маркетингового текста. [NativeSteamClient.cs](https://github.com/OpenSteamClient/OpenSteamworks/blob/master/OpenSteamworks/Native/NativeSteamClient.cs).

В июле 2025 автор описал работу над IPC и собственной реализацией внутренних API, чтобы UI перестал зависеть от нативных библиотек Valve. При этом он явно отмечал, что собственная реализация API ещё не начата. Поэтому планы этой переработки нельзя выдавать за существующий полностью независимый runtime. [Сообщение автора о следующей архитектуре](https://github.com/OpenSteamClient/OpenSteamClient/issues/56#issuecomment-3156875401).

### macOS

В обсуждении porting автор объяснял: если движок Steam доступен только в x86-64, нативный ARM UI требует отдельного процесса-хоста и IPC. Это хорошая архитектурная подсказка, но обсуждение датировано 2023 годом и не доказывает нынешнюю архитектуру Steam для Mac. Текущие Mach-O slices нужно измерить непосредственно на поставляемых библиотеках. Закрытие issue также не доказывает готовый порт. [macOS issue и комментарий Rosentti](https://github.com/OpenSteamClient/OpenSteamClient/issues/23#issuecomment-1679070979).

## 2. Mist: прямой macOS-пример без запущенного Steam

У `98przem/mist` нативный Swift-интерфейс, QR-вход, загрузчик на DepotDownloader и Windows-игры через Wine. Автор заявляет тестирование на Apple Silicon M2/macOS 15. Steam client не запускается. Cloud в опубликованной версии умеет восстановление, но не загрузку новых сохранений на сервер; overlay под Wine и игры с anti-cheat не поддерживаются. Это предметный технический результат, но не полный parity-клиент. [README Mist](https://github.com/98przem/mist).

В `MistApp.swift` видна другая игровая архитектура: при запуске интегрируется `gbe_fork`, заменяющий игровые Steam API DLL, оригинал сохраняется отдельно. После завершения игры achievements из локального состояния передаются helper-ом в Steam. Поэтому фразу «игра запускается без Steam» нельзя автоматически трактовать как «работают оригинальные multiplayer tickets, Steam Networking, VAC, invites и все SDK-вызовы». Это не метод OpenSteamClient с оригинальным `clientdll`. [MistApp.swift: игровой адаптер и запуск](https://github.com/98przem/mist/blob/main/MistApp.swift).

Практически полезно изучать у Mist разделение UI, авторизации, процесса загрузки, entitlement-данных и game lifecycle. Не следует считать подмену игровых API основой полной совместимости SkinOS. Для заявленной цели предпочтительнее сначала проверить оригинальный runtime, оставив самостоятельный протокол для библиотек, аккаунтов и общения. Это вывод для нашего проекта, а не обещание авторов Mist.

Есть также старый совершенно другой **Mist** Джейсона Чжана: Windows C# клиент, созданный вокруг SteamBot/SteamKit2 для торговли и общения. Совпадение названия не делает его macOS game launcher. [Авторская страница старого Mist](https://jzhang.net/mist/).

## 3. Полностью независимый runtime: Argon и argonx

Argon пытается воспроизвести `steamclient.dll` через C# и interop, то есть заменить сам backend, а не только предоставить заголовки. Автор описывает раннюю стадию: частично реализованы Friends/User, много IPC и callback-задач остаются открытыми. Это подтверждение возможности исследовать такой путь, но не доказательство работающей полной замены. [Argon](https://github.com/emily33901/Argon).

argonx — C++ вариант с целью binary interoperability. В README отмечены зависимости от конкретного ABI/компилятора. Здесь интересны client/server boundary и экспорт существующих интерфейсов; перенос исходников сам по себе не даёт актуальную совместимость. [argonx](https://github.com/emily33901/argonx).

Сам автор OpenSteamClient в обсуждении Argon предпочёл сначала использовать оригинальную библиотеку ради совместимости и рассматривать собственный runtime позже. Он отдельно указал, что API заметно меняется. [Позиция Rosentti](https://github.com/OpenSteamClient/OpenSteamClient/issues/45#issuecomment-2008049512).

## 4. Что подтверждено про Valve и удаления

**Публичного первичного подтверждения, что Valve потребовала удалить именно OpenSteamClient, OpenSteamworks, Argon или Mist, в проверенных источниках не найдено.** Репозитории доступны. Это не утверждение, что подобного никогда не происходило с другими проектами; конкретный случай пользователя пока не идентифицирован.

Нашлись два важных, но разных сообщения автора OpenSteamClient:

1. Он опасался, что самостоятельная реализация библиотеки может привести к претензиям и закрытию проекта. Формулировка описывает возможный будущий риск, не полученное требование. [Комментарий автора](https://github.com/OpenSteamClient/OpenSteamClient/issues/45#issuecomment-2051563930).
2. Он сообщил, что VAC-secured servers начали отключать пользователей OSC, тогда как раньше работали. В сообщении указано именно отключение, не бан, а вероятную причину автор обозначает как предположение. Это не repo takedown и не запрет авторизации во всех сервисах Steam. [Уточнение Rosentti](https://github.com/OpenSteamClient/OpenSteamClient/issues/45#issuecomment-2053723554).

В GitHub DMCA проверен полный список файлов и выборка уведомлений с Valve/Steam/Argon в имени. Например, уведомление Valve от 10 января 2024 относится к TF-Source-2 и игровым assets, а не к Steam-клиенту. Уведомления `argon-client` 2024 года называют другой проект (`argonmc`, репозитории `prohacker69420/argon` и `sootysplash/runnable-argon`), не `emily33901/Argon`. Совпадение названия не является подтверждением takedown нашего кандидата. [Valve/TF-Source-2](https://github.com/github/dmca/blob/master/2024/01/2024-01-10-valve.md), [другой Argon Client](https://github.com/github/dmca/blob/master/2024/10/2024-10-28-argon-client.md).

Поиск не дал основания превращать тезис «личное использование Valve не волнует» в установленный факт. Для разработки технический вывод уже достаточен: отсутствие официального UI достижимо; доступность каждой серверной функции определяется реальным испытанием, а не обещанием альтернативного клиента.

## 5. Рекомендуемое изменение плана SkinOS

Сделать **собственный Steam runtime host** главным исследовательским направлением вместо обязательного запуска Steam.app:

1. SwiftUI/AppKit или Tauri UI и Rust core остаются независимыми от внутреннего ABI Valve.
2. Отдельный `skinos-runtime-host` загружает совместимую библиотеку Valve и работает как global Steam instance.
3. Rust ↔ helper используют узкий типизированный IPC: login state, список приложений, installation state, launch, lifecycle, callbacks.
4. До запуска helper проверяет точную версию/архитектуру библиотек и наличие другого владельца Steam global state.
5. Первое доказательство: тестовая принадлежащая пользователю игра вызывает оригинальный Steam API и получает правильный SteamID без Steam.app/steamwebhelper.
6. Затем проверять конкретно achievements, Cloud, invitations, networking, Workshop и дополнительные игры. Покрытие фиксировать матрицей, не одним флагом «Steam работает».
7. Несколько аккаунтов библиотеки/магазина/чата не равны нескольким одновременно активным игровым runtime. Сначала реализовать безопасную последовательную смену владельца игрового runtime.

Это самостоятельный клиент по пользовательскому опыту и процессной архитектуре. Использование официального движка не требует сохранения официального UI. Полностью независимый бинарно совместимый runtime остаётся отдельной долгосрочной задачей; исследование не обнаружило готового компонента, гарантирующего все функции Steam на macOS.
