# Стек macOS-клиента: Rust, SwiftUI/AppKit и Tauri

Дата проверки первичных источников: 9 октября 2026 года. Это исследование для плана; измерения прототипов ещё не проводились. Оценки удобства разработки и рекомендации ниже — инженерное суждение, а не опубликованные сравнительные бенчмарки.

## Рекомендация

Для продукта, который делается прежде всего для macOS, выбрать **Rust core + SwiftUI с точечным AppKit + WKWebView для официальных веб-страниц Steam**. Библиотека, поиск, менеджер аккаунтов, очередь операций, друзья и собственные настройки должны быть собственным интерфейсом. Магазин и другие поверхности Valve, для которых нет подходящего поддерживаемого API, — отдельными веб-поверхностями.

Это сохраняет пожелание иметь основную логику на Rust и даёт прямой контроль над нативными окнами, меню, фокусом, доступностью и интеграцией macOS. SwiftUI не является гарантией отсутствия лагов: Apple отдельно документирует дорогие обновления и причины пропуска кадров. AppKit следует вводить там, где измерения или конкретные требования дают причину — например, сложная библиотечная сетка, drag-and-drop или управление окнами. SwiftUI официально поддерживает включение AppKit через `NSViewRepresentable`. [SwiftUI performance](https://developer.apple.com/documentation/Xcode/understanding-and-improving-swiftui-performance), [NSViewRepresentable](https://developer.apple.com/documentation/swiftui/nsviewrepresentable).

**Tauri 2 + Svelte + TypeScript — полноценный альтернативный кандидат**, особенно если главное — произвольные темы, быстрые визуальные итерации, веб-компетенции команды или последующий Windows/Linux-клиент. Предлагается короткий A/B-прототип до закрепления GUI. Решение не должно основываться на утверждениях «Swift всегда быстрее» или «Rust делает любой GUI быстрым».

Важно: оба варианта используют WKWebView для веб-страниц Valve на macOS. Переход с Tauri на Swift не исправляет саму тяжёлую страницу магазина и не создаёт отсутствующие Steam API. Tauri официально использует системный WebKit/WKWebView, версия которого зависит от ОС. [Webview Versions](https://tauri.app/reference/webview-versions/).

## Сравнение для этого продукта

| Критерий | SwiftUI/AppKit + Rust | Tauri 2 + Svelte/TS + Rust |
|---|---|---|
| Собственный интерфейс | Нативные представления; для точного поведения доступны AppKit-компоненты | HTML/CSS/JS в системном WKWebView |
| Свободная визуальная стилизация | Реализуема, но сложные собственные компоненты требуют Swift/AppKit-компетенций | CSS, дизайн-токены и веб-инструменты удобны для большого числа тем |
| macOS-интеграция | Прямой доступ из Swift к платформенным API | Штатные Tauri API и плагины; нестандартные возможности могут потребовать macOS-моста |
| Rust | Основная логика в Rust; отдельная FFI-граница и сборка | Rust — штатная серверная часть Tauri; граница IPC между UI и core |
| Магазин Valve | WKWebView, те же ограничения сайта и WebKit | WKWebView, те же ограничения сайта и WebKit |
| Мультиаккаунтные веб-профили | WKWebsiteDataStore с отдельным UUID | `data_store_identifier` в Tauri |
| Будущие Windows/Linux | Rust переносим, GUI придётся писать отдельно | Большая доля GUI может быть общей; всё равно нужны платформенные проверки |
| Основной риск | Две языковые экосистемы, FFI, жизненный цикл задач и Swift concurrency | DOM/layout, несколько WebView-процессов, аккуратная IPC-конфигурация |
| Производительность | Проверить на реальном сценарии | Проверить на том же сценарии |

Таблица сравнивает архитектуру и стоимость разработки, а не измеренный расход памяти. Возможность Svelte/TS и статического SPA подтверждена документацией Tauri; сама документация рекомендует Vite для подобных frontend-стеков. SSR-сервер для такого desktop shell не нужен. [Frontend Configuration](https://tauri.app/start/frontend/).

## Минимальная macOS и независимые аккаунты

**Предложение проекта: macOS 14+** как нижняя граница первой версии, с Apple Silicon как основной платформой разработки. Это наше проектное решение, не утверждение о минимальной версии macOS для самого Steam.

Причина: начиная с macOS 14, публичный API WebKit позволяет создавать несколько независимых постоянных `WKWebsiteDataStore` через UUID. До этого публичная модель давала несколько непостоянных хранилищ, но только одно постоянное — default. UUID необходимо сохранять, чтобы после перезапуска открыть прежний профиль. [WebKit: Building Profiles](https://webkit.org/blog/14423/building-profiles-with-new-webkit-api/).

Tauri предоставляет `WebviewWindowBuilder::data_store_identifier([u8; 16])`, доступный на macOS 14+; это замена недоступному в WKWebView произвольному `data_directory`. Swift и Tauri здесь используют одну платформенную возможность, поэтому Swift не снимает ограничение старых macOS. [Tauri Rust API](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindowBuilder.html#method.data_store_identifier).

Предлагаемая модель:

- У аккаунта есть стабильный внутренний `AccountId`, подтверждённый SteamID, UUID веб-профиля и отдельное пространство кэшей.
- Свежий аккаунт проходит собственный вход в назначенном ему профиле. При восстановлении сессии проверяется, что фактический SteamID соответствует выбранному аккаунту.
- Store/Community webviews одного аккаунта могут разделять его хранилище; аккаунты A и B получают разные хранилища.
- Новый WebView создаётся с нужным data store сразу. Не реализовывать переключение через глобальную перезапись cookie jar.
- Удаление аккаунта закрывает относящиеся к нему WebView, удаляет его веб-данные, локальные кэши и связанные секреты. WebKit документирует отдельные операции для данных профиля. [WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore).

Cookie store — только один слой изоляции. HTTP-клиенты Rust, токены протокола, websocket/chat-соединения, локальная БД, фоновые задания и события должны быть явно привязаны к `AccountId`. UI-поле «выбранный аккаунт» не должно автоматически менять владельца уже запущенной операции. Для завершений запросов нужен контекст аккаунта и поколение сессии: ответ старого входа после logout не должен обновлять новый профиль. Это проектные требования, а не свойства, автоматически предоставляемые WKWebView.

Не закладывать копирование cookie из официального Steam/Safari или одного профиля в другой как основной вход. Изоляция профилей не обещает переносимость сессий, не выполняет Steam Guard и не переключает локальную игровую сессию официального Steam. Проверка владельца перед покупкой/запуском и независимая проверка активного игрового аккаунта остаются отдельными задачами.

Секреты, которыми управляет приложение, хранить через Keychain; в SQLite — ссылки и несекретные метаданные. Не передавать refresh/access tokens в UI и логи. Apple предоставляет Keychain Services для небольших секретов и контроля доступа к ним. Это не означает, что WebKit-cookie автоматически лежат в нашем Keychain: их хранением управляет WebKit. [Keychain Services](https://developer.apple.com/documentation/security/keychain-services).

## Доверенные и внешние поверхности

У Tauri локальный интерфейс приложения должен иметь узкие команды вроде «получить страницу библиотеки», «создать намерение запуска» и «показать профиль». Удалённая страница Steam не должна получать shell, filesystem, произвольные HTTP-команды, Keychain или запуск игр через IPC. Для неё не задаётся remote API capability. По документации, remote API access требует явной настройки; при этом разработчик сам отвечает за Rust-команды и проверку их аргументов. [Tauri Capabilities](https://tauri.app/security/capabilities/).

Существенная тонкость: capability, назначенная целому окну через `windows`, распространяется на все его WebView. Для окна с локальным UI и удалённым контентом следует привязывать разрешения по **точным `webviews` labels**, исключать широкие шаблоны и проверять объединение capabilities. Документация прямо рекомендует webview-level scope для multiwebview windows. [Capability reference](https://tauri.app/reference/acl/capability/).

Дополнительные проектные правила:

- Отдельная локальная поверхность приложения и отдельный удалённый WebView; не смешивать страницу магазина с привилегированным DOM.
- Не внедрять секреты через JavaScript; не делать универсальный «выполнить JS / выполнить shell» мост.
- Переходы и новые окна магазина обрабатываются отдельной navigation policy. В платёжных потоках не ломать внешние redirects и bank challenge; точную политику сформировать после PoC.
- Произвольные внешние ссылки открывать через системный браузер. Процесс оплаты должен сохранять явный контекст аккаунта, даже когда часть потока ушла во внешний браузер.
- В Swift реализовать ту же границу: у внешнего WKWebView нет привилегированных script message handlers.
- Тестировать вредоносный iframe/redirect, замену аккаунта в момент операции и невозможность вызвать локальную команду со страницы магазина.

На стороне Swift это остаётся собственной архитектурой доступа; на стороне Tauri capabilities помогают её выразить, но не заменяют авторизацию команды внутри Rust.

## Связь Swift и Rust

Рекомендуемый старт — один Rust core, статическая библиотека и небольшой публичный FFI API через UniFFI. Не экспортировать весь граф внутренних объектов. Swift получает ограниченные DTO, доменные ошибки, идентификаторы заданий и батчи событий; Rust владеет сетью, планировщиком и состоянием аккаунтов. Для конкретных macOS-функций возможен обратный небольшой интерфейс платформенных служб.

UniFFI документирует production-quality Swift bindings, но текущая страница отдельно предупреждает о частичной поддержке Swift 6 и шероховатостях `Sendable`, в частности для async. Поэтому до выбора конкретной версии нужны сборка с выбранным Swift compiler mode и тесты callback/async-границ. Не считать это уже доказанной несовместимостью конкретного релиза. [UniFFI Swift bindings](https://mozilla.github.io/uniffi-rs/latest/swift/overview.html).

Асинхронная обёртка сама по себе не переносит тяжёлую работу с UI-потока. Ядро должно иметь явную модель runtime/worker queue, короткие обработчики и ограниченную очередь событий. UniFFI описывает как использование runtime внешнего языка, так и интеграцию собственного Rust runtime. [UniFFI async overview](https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html).

**Отмена операций — отдельный обязательный PoC.** В публичных материалах UniFFI есть расхождение: пользовательское описание futures говорит об отсутствии прямой поддержки отмены, тогда как internal FFI docs описывают `rust_future_cancel`, а changelog содержит исправления cancellation. Надёжнее закрепить релиз и проверить поведение Swift `Task.cancel()`, shutdown, таймаутов и дочерних Rust tasks, чем обещать конкретную семантику по одному абзацу документации. [Futures guide](https://mozilla.github.io/uniffi-rs/next/futures.html), [Async FFI details](https://mozilla.github.io/uniffi-rs/next/internals/async-ffi.html), [UniFFI changelog](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md).

Планировать прикладную отмену длительных операций по JobId независимо от FFI-механизма: остановка загрузки или смена аккаунта должна корректно завершать именно доменную операцию.

## Честное сравнение производительности

Сделать два тонких вертикальных прототипа с одинаковыми фикстурами и общим Rust core: библиотека, поиск, карточка игры, список друзей, переключатель аккаунта и один веб-магазин. Тратить время на одинаковый сценарий, а не на два полноценные клиента.

Матрица: release build; одна и та же машина; фиксированная версия macOS; одинаковые обложки и кэш; библиотеки 100/1 000/10 000 игр; 1/3/10 аккаунтов; открытый и закрытый магазин. Сначала локальные фикстуры для изоляции UI, затем реальная сеть. Разделить cold/warm start и первый кадр/готовность к взаимодействию/полную синхронизацию.

Измерять:

- p50/p95 запуска до интерактивной кэшированной библиотеки;
- p95 локального поиска и переключения разделов;
- frame hitches, main-thread stalls и плавность при обновлении presence;
- physical footprint всей группы процессов, CPU, wakeups и энергию в простое;
- рост памяти после многократных входов, переключений, открытия и закрытия webviews;
- поведение при sleep/wake, потере сети, большой загрузке и сворачивании окна.

Для SwiftUI доступны Instruments и специализированная диагностика view updates. Для обоих прототипов нужны системные CPU/memory/hang traces, для веб-части — DOM/layout/network profiling. [Apple performance analysis](https://developer.apple.com/documentation/swiftui/performance-analysis), [Understanding and improving SwiftUI performance](https://developer.apple.com/documentation/Xcode/understanding-and-improving-swiftui-performance).

Предлагаемые стартовые **целевые критерии продукта, не результаты замеров**: кэшированный экран после запуска p95 ≤ 1,5 с на согласованном минимальном Mac; локальный поиск по 10 000 играм p95 ≤ 50 мс; отсутствие видимых пропусков кадров при типовом скролле на 60 Гц; отсутствие монотонного роста памяти после 100 переключений аккаунтов. Конкретный memory/energy budget утвердить по прототипу и реальным устройствам.

Если совместимость требует работающего официального Steam, отчёт должен показывать и наше приложение отдельно, и **полный расход Steam + его helpers + наш клиент**. Иначе маленький собственный процесс может скрывать ухудшение итогового потребления. Закрытая страница магазина также должна отличаться от просто невидимой: скрытый WebView может продолжать работу, поэтому необходим замер жизненного цикла и выгрузка лишних поверхностей.

## Тестирование и распространение

Проверки Rust core, миграций БД и account-scoped команд не зависят от GUI. Нативные UI-проверки дополняются ручным прохождением Steam Guard, CAPTCHA, покупок и внешних payment redirects на тестовых аккаунтах; финансовые операции не выполнять фоновым тестом без специального сценария и разрешения.

Не закладывать обычный `tauri-driver` как готовый macOS E2E-путь. Текущая документация Tauri говорит, что системный desktop WebDriver доступен напрямую для Windows/Linux; для macOS она предлагает embedded WebDriver server сервиса CrabNebula с платным API key. Возможны также собственная macOS UI-автоматизация и отдельно browser component tests, но последние не заменяют проверку настоящего WKWebView. [Tauri WebDriver](https://tauri.app/develop/tests/webdriver/).

Для первой публичной macOS-версии предлагается подписанный и notarized DMG с проверяемыми обновлениями. Apple описывает Developer ID, Hardened Runtime, secure timestamp и подпись распространяемых executable-компонентов; наличие Rust helper не освобождает его от подписи. [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Developer ID](https://developer.apple.com/developer-id/).

У Tauri есть штатная документация подписи/notarization и поддержки обеих macOS-архитектур. У Swift путь идёт через Xcode и тот же сервис Apple. Закладывать проверку скачанного quarantine-marked артефакта на чистом Mac, обновления, отката и сохранности профилей. [Tauri macOS signing](https://tauri.app/distribute/sign/macos/).

## Вопросы, которые должен закрыть первый PoC

1. Работают ли вход, Steam Guard, Store/Community redirects и checkout в WKWebView на минимальной и текущей поддерживаемой macOS?
2. Изолированы ли два аккаунта после перезапуска, logout, удаления профиля и истечения сессии? Соответствует ли фактический SteamID подписи аккаунта в UI?
3. Можно ли корректно пройти платёжный challenge/внешний браузер без покупки с чужого профиля? Как возвращается результат?
4. Каковы полный footprint и задержки с нужным количеством аккаунтов и официальным Steam в режиме совместимости?
5. Проходит ли Swift/Rust bridge выбранные Swift 6 настройки, отмену, завершение приложения и нагрузку событиями?
6. Какой прототип быстрее реализует требуемый дизайн, оставаясь в согласованном performance budget?
7. Есть ли у multiwebview Tauri нужные поведение фокуса, доступность, popups, IME, resize и безопасная ACL-конфигурация без private API?
8. Проходит ли каждый кандидат signing/notarization и запуск скачанного DMG до масштабирования разработки?

После этих проверок закрепить один GUI. При равных результатах для macOS выбрать SwiftUI/AppKit; если Tauri даёт заметно более быстрые визуальные итерации и проходит те же performance/security criteria, выбрать Tauri. Rust core и account-модель в обоих случаях сохранить общими.
